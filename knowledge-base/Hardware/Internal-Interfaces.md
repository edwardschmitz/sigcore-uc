# Internal Interfaces

> **Engineering source draft.** This is a map of how Core addresses peripheral ICs *inside* SigCore UC. The I²C map is not an advertised external device communication protocol and is not a substitute for the .NET or HTTP APIs. Hardware addresses are evidence from the supplied source and Rev B schematic, not a guarantee for another board revision.

## 1. Architecture: Pi, control software and peripheral bus

The Raspberry Pi 4 Model B hosts Linux and the Core application. A 40-pin header brings power/ground and serial lines to the main I/O board. The schematic identifies **GPIO2/SDA (physical header pin 3)** and **GPIO3/SCL (physical header pin 5)** for I²C. `SigCoreCommon` drivers open **Linux `/dev/i2c-1` / I²C bus 1** in the reviewed source. Sheet 1 also contains an **NXP PCA9306 bidirectional level translator** and pull-up components for differing on-board logic domains. This does not galvanically isolate field devices.

```text
  Raspberry Pi 4 / Linux / Core
           |
       I2C bus 1
           |
  local level translation, pullups
           |
   +-------+----------+-----------+---------+---------+
   |       |          |           |         |         |
 Relay    DI          AI range    ADC      PWM       DAC
 GPIO     GPIO        selector    ADS1115  PCA9685   MCP4728
 expander expander    MCP23017             AO mode  4 AO
 MCP23008 MCP23008                        select   voltages
   |       |          |           |         |         |
 ULN2803A NPN input  TMUX1209s <-+---------+--> AO muxes
   |       |          |                     |
  R1-R8   DI1-DI8    AI1-AI4             AO1-AO4
```

This is a conceptual map, **not a pin-for-pin wiring or real-time signal propagation diagram**. Some analog control signals are produced through expander GPIOs rather than direct Pi pins; see below.

## 2. Internal I²C address map

| Address (7-bit) | Device | Role | Implementation evidence |
|---|---|---|---|
| `0x20` | MCP23008 | Eight relay-control GPIO outputs, through ULN2803A coil drivers | `RELAY_OUT.cs`, `Mcp23008Driver.cs` |
| `0x21` | MCP23008 | Eight sensed digital-input GPIO values after NPN conditioning | `D_IN.cs`, `Mcp23008Driver.cs` |
| `0x22` | MCP23017 | Analog input switch-selection/address/enable lines | `A-DOUT.cs`, `Mcp23017Driver.cs` |
| `0x40` | PCA9685 | PWM generation and DAC/PWM output selection via switched routes | `PCA9685.cs`, `PWM_OUT.cs`, `A_OUT.cs` |
| `0x48` | ADS1115 | Shared ADC for four configured analog input measurement paths | `A_IN.cs`, `Ads1115Driver.cs` |
| `0x60` | MCP4728 | Four-channel voltage DAC | `A_OUT.cs`, `Mcp4728Driver.cs` |

The listed values are **bus addresses**, not TCP ports or analog channel numbers. The `MCP23008` relay and DI devices share a part family but have **distinct addresses and directions**. The `PCA9685` handles more than four PWM waveforms because its channels are also used to select analog-output signal paths. Software users should not try to manipulate these registers directly as an alternative to Core.

## 3. Path-by-path ownership

### Relay output path

`Core -> I²C 0x20 MCP23008 output -> ULN2803A low-side drivers -> 5 V coils -> mechanical COM/NO/NC contacts`. Hardware lacks independent contact-position sensing in reviewed source; logical state may be inverted relative to coil energization. See [Relay Outputs](Relay-Outputs.md).

### Digital input path

`DI field voltage referenced to GND -> per-channel resistor/ESD/transistor network -> active-low output -> I²C 0x21 MCP23008 input -> Core logical polarity and debounce`. The schematic mentions “isolated” despite sharing common ground; **not galvanically isolated**. See [Digital Inputs](Digital-Inputs.md).

### Analog input path

`Sensor signal -> channel-specific input mode network and TMUX1209 -> ADS1115 -> calibration/scaling -> Core value`, while `MCP23017` provides switch-selection outputs. Multiple inputs share conversion resources; a configured converter data rate is **not** the per-channel refresh rate. See [Analog Inputs](Analog-Inputs.md) and [Measurement and Control Timing](../Core-Software/Measurement-and-Control-Timing.md).

### Analog output path

`Core setpoint/PID command -> MCP4728 voltage DAC OR PCA9685 PWM -> SN74LVC1G3157 selection switch -> field AO`. In this design, selection lines are generated by the PWM peripheral and passed through analog switches. Commanded value is not an independently sensed output voltage. Scaling behavior in the reviewed source conflicts with parts of published text; see [Analog Outputs](Analog-Outputs.md).

## 4. Other internal hardware paths

- **REF3025 2.500 V reference:** analog precision/reference function shown in sheet 3. It is an electrical reference, not I²C-addressable memory or a software telemetry channel by itself.
- **PCA9306:** level translation for internal I²C electrical domains. Its presence does not allow arbitrary 5 V logic to be connected to Raspberry Pi GPIO headers.
- **Power/Ready indicators:** schematic sheet 1 includes LED circuitry; an LED's illuminated state does not certify Core process readiness or proper physical I/O operation.
- **EPD design signals:** header/net labels for e-paper/SPI-like lines are present on sheet 1. **Do not infer an installed or supported front-panel e-paper feature** from those nets. Planned display work belongs to a later revision.
- **FRAM migration code:** supplied `Fm24cl64bDriver.cs` is evidence of a legacy FRAM facility; active Core configuration persists in `properties.json`. Presence of a legacy driver does not mean new configuration is necessarily being written to FRAM.
- **Network interfaces:** Ethernet/Wi-Fi are Raspberry Pi OS interfaces and not part of the I²C peripheral bus. The network-accessible SigCore interfaces are documented separately.

## 5. Service and integration rules

The Core process **owns** the physical I/O bus. Introducing an independent program that writes to the same device addresses can conflict with Core's state and timing, alter relay coils or outputs, bypass validation and produce unrecoverable mismatch between actual hardware and reported state. The customer integration boundary is the managed native protocol or published device-site API. Even an internal engineering diagnostic script must explicitly coordinate bus ownership and external load safety.

Use [Programming/Discovery and Connections](../Programming/Discovery-and-Connections.md) for mDNS and TCP 7020; [Software Architecture](../Architecture/Software-Architecture.md) for WebBridge and clients. **Modbus:** a file named `ModbusCleint.cs` exists in the source tree, but this does *not* establish a general-purpose SigCore Modbus TCP server or supported Modbus register map.
